# Parallel cloud E: implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement task-by-task.

**Goal:** Build a separately tested cloud E: attachment candidate without touching working C:/D: or production startup.
**Architecture:** Python validates native Windows inventory and emits a constrained read-only mount plan. PowerShell supplies inventory and executes only the validated disk-specific actions, with owned-action rollback. An E-only fsync/readback probe and disposable Windows tests expose identity/collision failures.
**Tech Stack:** Standard-library Python3, native Windows Storage/iSCSI cmdlets, GitHub CI.
**Spec:** docs/superpowers/specs/2026-10-13-cloud-e-design.md

## Global Constraints
- Candidate letter E only; C/D and production workflow untouched.
- No format/init/clear in production; existing sessions unchanged.
- Read-only attach until real-cloud exclusive-owner and zero-cost evidence exist.
- No credentials in source/logs or operational secrets/tailnet in CI.

## Review Focus
- E occupied by nonfilesystem mappings or another disk: reject before any disk mutation.
- Portal/IQN identity differs or duplicate matches: reject without selecting the first disk.
- Failure after mounting: remove only this invocation's E path and restore original flags/session.
- Marker/canary path is a reparse point: reject rather than write elsewhere.
- Local readback/CI fixture: explicitly not cloud crash/reboot persistence proof.
